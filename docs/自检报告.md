## 二、第 101 条为什么不达标，以及怎么补救

### 现状

```
GET /api/v1/platforms
  platforms: [ feishu ]              ← 只有 1 个在线
  configured: { feishu: true, dingtalk: false, telegram: false, email: false }
  connectable: [email, telegram, feishu, dingtalk]   ← 代码都在，只是没凭证
```

数据库里还留着历史：`email` 有 1 条入站消息、`feishu_web` 有 1 条，说明这两个通道**曾经跑通过**，后来凭证被停用/删掉了。

### 三条补救路径，按成本排序

| 路径 | 耗时 | 前提 | 风险 |
|---|---|---|---|
| **A. 重填 QQ 邮箱授权码** | 5 分钟 | 你能登录 QQ 邮箱、开 IMAP 拿到授权码 | 无 |
| **B. 接 Telegram Bot** | 10 分钟 | 梯子能访问 `api.telegram.org` | 网络可能不通 |
| **C. 用 RPA 采集器补一个"飞书网页"** | 0 分钟 | 已跑通，只是当前没有实时消息 | 采集器只读，不能发 |

**建议 A**，因为邮箱同时满足"官方协议 + 能收能发 + 能发文件"，而且之前已经验证过全链路。

## 三、宣讲会五条变更

| # | 宣讲会要求 | 现状 | 判定 |
|---|---|---|---|
| 1 | 初赛推迟到 11 月 22 日 | — | 时间信息，已记录 |
| 2 | 无 API 时可用 RPA 模拟鼠标键盘"拷贝消息并**发送**" | 有网页版采集器，**只读不写** | **部分达标** |
| 3 | 闭环含：用户注册 / 配置平台 / 朋友清单或消息列表 / 选联系人发送 / 自动或人工回复 | 五项全部实现并实测 | **达标** |
| 4 | 实现"平台内**个体用户之间**"的文本消息发送 | 飞书是"用户 ↔ 机器人"，中间过一层应用身份 | **不达标（结构性问题）** |
| 5 | 严禁直接提交 AI 生成结果，须附对话过程链接 | 已导出会话 `ai-session-export/`，含 16,443 条原始事件 | 达标 |

### 第 2 条：RPA 缺"发送"

采集器 `scripts/collect-feishu-web.mjs` 只做读取 + POST 到 `/api/v1/ingest`。宣讲会原文要求"拷贝消息并发送"，**发不出去就等于只做了半个**。

补法：在采集器里加一个"在飞书网页版输入框里打字并回车"的动作。技术上可行（ego 能点能输入），但会和现有 Outbox 投递链路重复，需要决定走哪条路。

### 第 4 条：这是最根本的偏差

赛题原文第 101 行只说要"对接平台"，但宣讲会把它解释成"平台内个体用户之间的消息"。我们做的是经典的"机器人中转"模式：

```
你 → 机器人（飞书应用）→ 我们的系统 → 机器人 → 对方
```

而宣讲会想要的是：

```
你 → 对方的飞书账号（直接，不经机器人）
```

**这条路走不通的原因不是技术，是平台权限**：
- 飞书自建应用的用户身份读不到消息（`im:message.*:get_as_user` 不对外开放，实测 400 code=230027）；
- 钉钉要"会话内容存档"（企业付费能力）；
- 唯一能做的是 RPA（以用户身份操作客户端）。

所以第 2 条和第 4 条是同一个答案：**RPA 做完整了，第 4 条才成立。**
