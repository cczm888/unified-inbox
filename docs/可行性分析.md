# 赛题 A 可行性分析

## 一、技术可行性

### 1.1 关键技术的成熟度

| 技术点 | 方案 | 成熟度 | 风险 |
| --- | --- | --- | --- |
| 飞书消息接收 | `lark-oapi` WebSocket 长连接 | 官方 SDK，稳定 | 需在开放平台把事件订阅方式改为「长连接」；漏改则收不到任何事件 |
| 飞书消息发送 | `im/v1/messages` + tenant_access_token | 官方 REST | token 有效期 2h，必须缓存并刷新 |
| 钉钉消息接收 | `dingtalk-stream` Stream 模式 | 官方 SDK | 需在应用内「机器人」页把消息接收模式选 Stream，否则 Stream 客户端握手失败 |
| 钉钉消息发送 | `sessionWebhook`（会话级临时地址） | 官方 | webhook 有效期约 1.5h，过期后需兜底走 `robot/groupMessages/send` |
| Telegram | Bot API `getUpdates` 长轮询 | 极度稳定 | 无 |
| 统一格式转换 | 自研 `UnifiedMessage` | — | 字段遗漏导致前端展示不全，用单测锁死字段集合 |
| 异步与并发 | FastAPI + async SQLAlchemy + Redis | 成熟 | SDK 回调在独立线程，需要用 `run_coroutine_threadsafe` 回主 loop |
| 可靠投递 | Outbox + `FOR UPDATE SKIP LOCKED` | 工业界标准模式 | 需要 PostgreSQL 9.5+，本方案用 16 |
| 实时推送 | SSE | 简单可靠 | nginx 必须关 buffering，否则前端"不实时" |

### 1.2 已完成的预研验证

- 三个适配器的转换逻辑已实现并配单测（无需任何凭证即可跑）；
- 长连接/长轮询都不要求公网回调地址 —— **本题最大的可行性风险已排除**；
- 全链路容器化，本地与服务器行为一致。

### 1.3 技术难点与应对

| 难点 | 应对 |
| --- | --- |
| 平台 SDK 在子线程回调 | 适配器统一 `_emit()` → `run_coroutine_threadsafe` 抛回主 loop，避免跨线程操作 session |
| 钉钉限流严格（单聊 20 条/分钟） | Redis 令牌桶 + outbox 延后重试，不阻塞用户操作 |
| 平台消息 ID 语义不同 | 统一 `platform + platform_msg_id` 复合唯一键；Telegram 拼 `chat_id:message_id` |
| 文件消息 | 飞书走 `im/v1/files` 上传换 file_key；Telegram 走 `sendDocument`；钉钉文件发送降级为文字提示（决赛补齐 media/upload） |

## 二、数据可行性

- **数据自产**：消息全部来自我们自己注册的机器人，不依赖任何第三方数据集、不需要爬虫、不涉及隐私数据合规问题。
- **数据量**：演示阶段每天几百条足够；表设计已考虑分页与索引（`created_at`、`platform+status`），十万级无压力。
- **数据留存**：`raw` 字段保留平台原始 JSON，赛后可用于复盘与补字段；`event_log` 保留原始事件流。
- **AI 数据**：只把消息正文发给 LLM 做摘要，不含用户标识；未配 Key 时自动降级为规则，不阻塞演示。

## 四、风险与预案

| 风险 | 概率 | 影响 | 预案 |
| --- | --- | --- | --- |
| 抽签没抽到赛题 A | 中 | 高 | 赛题 B/C 的需求文档已同步阅读，B 的 OCR 与 C 的简历生成可复用本项目的异步任务与 LLM 层 |
| 飞书应用审核不通过/事件订阅配错 | 中 | 高 | 钉钉 + Telegram 两个平台已可独立构成「≥2 平台」的完整闭环，飞书仅影响 +3 加分 |
| 服务器无法访问外网平台 API | 低 | 高 | 部署在本地机器演示；容器只需出站 443 |
| 钉钉限流导致演示卡顿 | 中 | 中 | 令牌桶 + 队列；演示脚本控制发送频率，并在看板展示队列消化过程作为亮点 |
| LLM Key 失效/超时 | 中 | 低 | 规则降级路径已实现，界面明确标注「规则降级」 |
| 队员时间冲突 | 中 | 中 | 模块解耦（适配器/业务/前端），1 人也能推进；文档与代码同步提交 |
| docker 环境差异 | 低 | 中 | 提供非 Docker 本地运行说明（venv + npm run dev） |

## 五、结论

- **技术可行**：全部使用官方 SDK 与成熟框架，无自研协议，无公网依赖；
- **数据可行**：数据完全自产，无外部数据源与合规风险；
- **时间可行**：初赛前有 2 周可完成闭环 MVP，决赛前有 4 周做增强；
- **风险可控**：任一平台失效都不影响「≥2 平台闭环」这条硬性要求。
