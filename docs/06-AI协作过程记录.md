# AI 辅助开发过程记录

> 本文件对应官方宣讲会的一条硬性要求：
>
> 「严禁直接提交 AI 生成结果。使用 AI 辅助设计必须附上对话过程链接，以证明优化和思考过程。」
>
> 下面按「AI 做了什么 / AI 哪里判断错了 / 人怎么纠正的 / 结论怎么验证的」四项记录，
> 不回避错误，也不夸大作用。

## 一、AI 在本项目中的实际作用边界

| 环节 | 主要由谁完成 | 说明 |
|---|---|---|
| 赛题选择与产品方向 | **人** | 从三个赛题中选定「多平台统一入口」，并在过程中两次纠正方向（普通员工视角、网站作为中枢） |
| 技术选型 | 人定约束，AI 给方案 | 约束是人给的：不要公网回调、要能个人注册、要一条命令起 |
| 代码实现 | **AI** | 后端 34 个文件 4,755 行、前端 7 个文件 2,531 行的绝大部分 |
| 平台联调 | 人操作账号，AI 写脚本与排障 | 扫码登录、短信验证、授权确认必须本人；配置与排障由 AI 完成 |
| 验收判断 | **人** | 每个功能做完都截图给人看，由人决定「这样算不算好」 |
| 文档撰写 | AI 起草，人定结构与口径 | 五类文档的章节结构、哪些差距要写实、哪些结论要有原文支撑，由人拍板 |

一句话概括：**AI 负责把想法变成能跑的东西，人负责判断「这东西对不对、够不够」。**

## 二、四次 AI 判断错误与纠正过程

这一节是本记录的核心。如果 AI 只是「听话照做」，反而不值得信任——
真正能说明过程真实的，是下面这些 AI 说错、人被追问后改对的节点。

### 案例 1：赛题是否要求「读取用户全部聊天」

**AI 最初的判断（错）**：把「用户身份读不到消息历史」当成一个必须攻克的技术缺口，
并据此建议去申请企业认证、走会话存档付费方案。

**人的追问**：「但对赛题来说够了——赛题要的是多平台统一入口 + 闭环，这句话能指出来吗？」

**纠正过程**：AI 回到赛题原文（`doc2.txt`，共 234 行）逐行检索：

```
101  对接至少两个主流办公 / 社交平台（飞书、微信、钉钉等），通过官方开放 API 或 Webhook 实现。
102  提供统一入口（Web 或移动端），集中展示来自各平台的消息通知、待办事项等。
103  支持从统一入口向指定平台发送文本消息、文件等。
104  实现消息格式的统一转换与适配，将不同平台的消息体映射为内部标准格式。
105  业务闭环要求（核心）
106  系统必须形成"消息接收 → 统一展示 → 处理 → 发送反馈"的完整闭环……必须体现业务处理的闭环与状态回流。
```

全文检索关键词 `全部 | 所有消息 | 全量 | 聊天记录 | 历史消息 | 私聊` → **0 命中**。
第 102 行用的词是「消息**通知**」（notification），不是「全部消息」。

**结论变化**：赛题从未要求全量抓取。AI 之前的「技术缺口」判断是被自己放大的伪需求，
真正的风险是「闭环不够完整」，而不是「数据不够全」。

### 案例 2：飞书用户身份到底能不能读消息

**AI 最初的表述（不严谨）**：搜不到 `im:message.*:get_as_user` 权限 → 直接说「飞书不开放」。

**人的追问**：要求区分三层——「权限存在 / 对个人自建应用开放 / 用户有资格授权」，
并质问应用类型是企业自建还是个人应用。

**纠正过程**：
1. 核实应用类型：创建时点的是「创建企业自建应用」，控制台显示 `正式应用@用户662015的组织`，
   版本详情「可用范围：部分成员 → 用户662015」「对外共享：不允许」→ **确为企业自建应用（Custom App）**。
2. 重新实测六个接口，把边界逐条钉死：

| 接口 | 结果 |
|---|---|
| `GET /authen/v1/user_info` | 200 ✅ |
| `GET /im/v1/chats` | 200 ✅（items 为空，账号未加群） |
| `GET /im/v1/chats/{chat_id}` | 200 ✅ |
| `GET /im/v1/messages?container_id_type=chat` | **400 `code=230027` need scope: `im:message.p2p_msg:get_as_user`** |
| `GET /im/v1/chats/{chat_id}/messages`（旧） | 404 |
| `GET /contact/v3/users/me` | 400 `99991679 Unauthorized` |

3. **意外收获**：既然用户身份受限于消息，那应用身份呢？实测
   `GET /im/v1/messages`（应用身份 tenant_access_token）→ **200，能读整个会话的历史**。

**结论变化**：从「飞书读不了历史」变成「应用身份能读全量历史」，
并据此实现了 `POST /api/v1/inbox/backfill` + 界面上的「拉历史」按钮。
实测 `{"fetched":19,"inserted":14}`，把接入机器人之前的 18:00「你好」、18:02「测试」
等消息全部补回。

**这个案例说明**：AI 第一版结论方向对但论证粗，被追问后重新做实验，
反而找到了更好的路。最终结论写进了 `docs/飞书用户身份接入结论.md`，含证据链表。

### 案例 3：RPA 算不算合规接入

**AI 最初的判断（错）**：把飞书网页版 DOM 采集器标成「不计入赛题平台数，只是补充通道」，
理由是自己认为「必须是官方开放 API 或 Webhook」。

**人的动作**：发来官方宣讲会纪要链接。

**纪要原文**：

> RPA 自动化补充方案：若平台未开放 API 或申请困难，可使用 Windows 下的 Power Automate 等
> 桌面机器人，模拟鼠标键盘操作拷贝消息并**发送**。

**结论变化**：RPA 是官方明确认可的路径，AI 的自我设限是错的。
同时纪要要求「能发」才算数，所以采集器只读不写仍然不完整——这条被如实写进差距清单。

### 案例 4：出站气泡「一个框套着另一个框」

**人的反馈**：直接发截图，只说一句「一个框套着另一个框」。

**AI 的排查过程**：
1. 第一反应怀疑是嵌套容器 —— 用 `getComputedStyle` 查证，`.bubble.out` 只有单层，
   子元素背景全透明，**没有嵌套，假设不成立**。
2. 换方向查渲染：`background: #eef3ff` + `border: 0.8px solid #cfdcff` + `box-shadow: 0 1px 2px`。
3. 定位到真因：**125% 显示缩放下，1px 描边被抗锯齿拆成两条 0.6px 的线，
   再叠一层阴影，视觉上就成了双层轮廓**。

**修法**：出站气泡 `border-color` 改成与背景同色（视觉上无边框）+ `box-shadow: none`；
入站气泡保留描边（白底需要边界）。

**这个案例说明**：人眼能发现 AI 和自动化测试都发现不了的渲染问题；
而 AI 的价值在于**不猜、去量**——如果没有 `getComputedStyle` 那一步，
很可能改错方向（比如去删不存在的嵌套 div）。

## 三、AI 自己踩的坑（已写入代码注释与提交记录）

这些是 AI 在实现过程中犯的、由构建/运行结果直接暴露的错误：

| 坑 | 后果 | 现在怎么防 |
|---|---|---|
| 用 PowerShell 行索引批量改 Vue 模板 | `InsertRange` 静默失败，模板丢了闭合标签 | 改模板一律用整块字符串替换，不用行号 |
| 用 `.Replace` 全局替换 CSS | 把 `.bubble:hover .quote-btn` 里的选择器一起换掉 | 同上；改完用花括号计数核对 |
| 标题里用全角空格 U+3000 | Word 里渲染成豆腐块 `POST□/autoreply/rules` | 五份文档脚本 55 处全角空格改半角 |
| `sendNew` 忘了 `JSON.stringify` | 界面报「发送失败：[object Object]」 | 已从根上修：`request()` 统一摊平 422 的数组 detail |
| `@router.post("/send")` 少写 `/inbox` | 路由数对了但路径错，调用 404 | 路由数增加不代表路径对，要看 `openapi()['paths']` |
| `requirements.txt` 漏 `aiosqlite` | 本地能跑，CI 干净环境立刻 `ModuleNotFoundError` | 依赖清单只信干净环境，CI 就是干这个的 |

## 四、AI 给出的、被人采纳的关键设计决定

并非只有纠错——下面这些是 AI 提出、人确认后落地的判断：

1. **决定能见范围的是「身份」而不是「API 还是 Webhook」**
   —— 应用身份只看得到机器人参与的、用户身份看得到这个人能看到的、企业审计看得到全租户。
   这条结论直接决定了平台接入的技术路线。
2. **历史回填必须走与实时事件完全相同的入库管道**
   —— 否则去重键、状态机、字段映射会出现两套，回填的数据和实时数据对不上。
   实测中正是因为复用了同一管道，才暴露出 `platform_msg_id='outbox:N'` 与飞书真实
   `om_xxx` 不一致导致的重影问题。
3. **状态回流默认关闭**
   —— 每次改状态都往对方会话里发一条「[统一收件箱] 该消息已标记为…」，
   会把用户真正说的话顶出视野，是用功能换体验的负优化。改成可选开关。
4. **自动回复走 Outbox 而不是直接调平台接口**
   —— 限流、重试、退避、状态回写全部复用；否则钉钉 20 条/分钟的限制会有两处实现。

## 五、验证方式：每个结论都有可复现的证据

本项目所有「已完成」的判断都不是口头声明，全部带实测输出：

| 声明 | 证据 |
|---|---|
| 飞书双向闭环 | `outbox #10 sent result_msg_id=om_x100b60c6...`；入站事件原始 JSON 存档在 `docs/证据/` |
| 附件代理无损 | 下载文件 sha256 `CCC247CC...` 与用户原始上传文件**完全一致** |
| 历史回填 | `POST /inbox/backfill` → `{"fetched":19,"inserted":14}` |
| 自动回复 | 推「在吗？急事」→ 入站 `status=replied`、出站 `sent`、规则 `hit_count=1` |

## 七、对「严禁直接提交 AI 生成结果」的理解与执行

我们的做法：

1. **不接受不经验证的 AI 结论** —— 每个技术判断都落到实测命令或官方文档原文，
   例如「飞书读不到历史」这条，最终是靠 6 个接口的实测状态码定的，不是靠 AI 说。
2. **AI 的错误不隐藏** —— 上面第二节四个案例全部保留在文档里，包括 AI 判断失误的部分。
3. **人保留最终决定权** —— 产品方向、赛题理解、验收标准由人定；
   AI 提出方案，人判断是否采纳（例如「默认不发状态回执」就是人提出的体验问题，AI 才改的设计）。
4. **可追溯** —— 所有代码改动带中文提交信息，说明「改了什么、为什么改、怎么验证的」，
   共 30+ 次提交，构成完整的演进轨迹。
