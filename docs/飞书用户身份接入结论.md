# 飞书用户身份接入：结论与止损记录

> 记录日期：2026-11-03
> 触发：《Unified_Inbox_源码审查与飞书用户身份接入方案.md》第 5 节「Lark CLI User OAuth 接入可行性」
> 结论：**该路线已到止损点。不是技术做不了，是平台不给我们那个权限。**

## 0. 一句话

文件里写的止损条件是「如果应用权限目录没有目标 scope，或者平台拒绝该类型应用申请，就无需开发 CLI 子进程桥接」。这两条我们都已经撞到，所以不建 CLI 桥接，改走应用身份。

## 1. 证据链（全部为 2026-11-02 实测，非文档记载）

同一个接口，两种身份，两种结果：

| # | 接口 | 身份 | 结果 | 判读 |
|---|---|---|---|---|
| 1 | `GET /open-apis/im/v1/messages?container_id_type=chat&container_id=oc_xxx` | **应用身份**（`tenant_access_token`） | **200 code=0**，返回真实消息 | 机器人能读该会话全部历史，不限于订阅之后 |
| 2 | 同上 | **用户身份**（`user_access_token`） | **400 `code=230027 msg=Lack of necessary permissions, ext=need scope: im:message.p2p_msg:get_as_user`** | 用户身份反而读不到 |
| 3 | `GET /open-apis/im/v1/chats` | 用户身份 | 200 code=0，`items` 为空 | 能列群，但该账号未加群；不含 p2p 单聊 |
| 4 | `GET /open-apis/im/v1/chats/{chat_id}` | 用户身份 | 200 code=0 | 群详情可读 |
| 5 | `GET /open-apis/im/v1/chats/{chat_id}/messages`（旧接口） | 用户身份 | **404** | 接口已下线 |
| 6 | `GET /open-apis/authen/v1/user_info` | 用户身份 | 200 code=0 | 账号信息可读 |
| 7 | `GET /open-apis/contact/v3/users/me` | 用户身份 | **400 `99991679 Unauthorized … Please request user re-auth`** | 通讯录不在授权范围 |

**第 1 行和第 2 行的对照是全部要点**：不是「用户身份权限不够所以什么都做不了」，而是「用户身份比应用身份**更受限**」。这在直觉上反常，但机制清楚——`get_as_user` 系列 scope 属于敏感权限，向企业认证应用开放，不向个人租户的自建应用开放。

## 2. 权限目录的实际检索结果

在 `https://open.feishu.cn/app/cli_aa62e14639795c0d/auth`（权限管理）里搜：

| 搜索词 | 命中 |
|---|---|
| `get_as_user` | **0 条** |
| `p2p_msg` | 只命中 `im:message.p2p_msg:readonly`（**应用身份**，读用户发给机器人的单聊消息） |
| `offline_access` / `持续访问` / `离线` / `refresh` | **0 条**（这个 scope 也拿不到，见 §4） |

搜不到 = 申请不到。没有这个 scope，`user_access_token` 拿在手里也调不动第 1 行那个接口。

## 3. 为什么 Lark CLI 不改变结论

CLI 是官方 API 的封装，`--as user` 只是「用 user token 发请求」，不是「以特权身份发请求」。同一份 token、同一套 scope 校验、同一个 400。

所以文件 §5.4 的第 2 阶段（权限核验）就是我们的**终点**，第 3–6 阶段（会话列表 → 历史读取 → 抽样对比 → 集成评估）没有可执行的输入。

## 4. 复现方式（供复核）

```bash
# 应用身份：能读历史
GET https://open.feishu.cn/open-apis/im/v1/messages
    ?container_id_type=chat&container_id=oc_xxx&sort_type=ByCreateTimeDesc&page_size=5
Authorization: Bearer t-xxxxx          # tenant_access_token

# 用户身份：读不到
GET 同上
Authorization: Bearer u-xxxxx          # user_access_token
→ 400 {"code":230027,"msg":"Lack of necessary permissions",
       "error":{"message":"...need scope: im:message.p2p_msg:get_as_user"}}
```

取 `tenant_access_token`：`POST /open-apis/auth/v3/tenant_access_token/internal`，body `{app_id, app_secret}`。
取 `user_access_token`：走 OAuth 授权码流程（我们已实现，见 `backend/app/api/auth.py`）。

## 5. 这条路线真正的价值在哪

止损不等于没收获。第 1 行那个 200 是一个比「用户身份读全部会话」更贴合需求的发现：

**机器人能读它所在会话的全部历史，不限于订阅之后的消息。**

这意味着「用户在我接机器人之前的聊天」不需要用户身份也能补回来——只要机器人进了那个会话。已经落地成功能：

- `POST /api/v1/inbox/backfill?platform=feishu&chat_id=xxx&limit=50`
- 前端会话头部「拉历史」按钮
- 实测 `{"ok":true,"fetched":19,"inserted":14}`，11-02 18:00「你好」、18:02「测试」、18:09「abc」等接机器人之前的话全部回填成功

覆盖范围的真实边界：**机器人所在的会话**（单聊 + 它被拉进的群）全历史；机器人不在的会话，看不到。

## 6. 采纳文件里的三条建议

| 建议 | 状态 | 说明 |
|---|---|---|
| 优先级：第二平台 + 独立部署 > 用户身份历史 | **已采纳** | 与比赛评分直接相关（硬要求 2 平台 + 部署 20 分），用户身份不产生分数 |
| 源码审查的问题要在最新代码上复核 | **已采纳** | ZIP 审查的 11 条已逐条核实并修完，commit `15b5b75` |
| Bot/User 双来源的唯一键冲突 | **已预埋** | `message` 表 `UniqueConstraint(platform, platform_msg_id)`；`account_id` 区分来源（Bot 为 NULL，User 为 FK）。真正接入 User 通道前需改为 `(account_id, platform, platform_msg_id)`，否则跨账号同 ID 会串数据 |

## 7. 剩余可选项（按性价比排序）

| 选项 | 门槛 | 值不值 |
|---|---|---|
| 企业认证（让应用变成「已验证」） | 需营业执照 | 唯一能拿到 `get_as_user` 的合规路径，但个人参赛队没有 |
| 会话内容存档 | 企业开通 + 付费 + 签授权协议 | 钉钉/飞书都有，面向合规审计，不是个人开发者选项 |
| Telegram 用户账号（Telethon） | 零审批，手机号登录一次 | **性价比最高**，协议层就开放全部会话 + 历史。但 Telegram 的 MTProto 用户客户端算不算「官方开放 API 或 Webhook」，需要向赛方确认 |
| 屏幕读取（UIA + OCR） | 零审批 | 明确不符合赛题「官方开放 API 或 Webhook」，只作为兜底演示 |

## 8. 文档口径（对外只这么说）

> 飞书接入采用**应用身份**（企业自建应用 + 长连接事件订阅 + OpenAPI）。实时消息通过 `im.message.receive_v1` 事件推送，历史消息通过 `im/v1/messages` 按会话分页回填，发送通过 `im/v1/messages` 与 `im/v1/files`。
>
> 用户身份 OAuth 已实现授权链路（`/api/v1/auth/feishu/url` → 回调落库 → 自动续期），可读取账号与群组目录。**消息正文的用户身份读取未获平台授权**：`im:message.*:get_as_user` 系列 scope 不在个人租户自建应用的权限目录内，接口返回 `230027`。因此历史消息统一走应用身份回填，覆盖范围为机器人所在会话。

不要写成「不支持用户身份」——支持了，OAuth 跑通了；卡住的是消息正文这一个 scope。
